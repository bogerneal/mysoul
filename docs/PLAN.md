# 開發計畫與驗收標準

狀態：M0 文件初稿完成；M1 兩份真實樣本的解析與縣市／時段契約已核對，溫度缺值語意仍待確認；M2 本機真實更新、儲存與查詢已打通，更新政策／日誌待整合；M3–M5 尚未實作。真實整合詳見 [LIVE_CONTRACT.md](LIVE_CONTRACT.md)。

## 1. 使用者與目標

- 一般使用者：快速比較指定縣市在未來一週的最高／最低溫與日期差異。
- 學習者：理解 API → JSON → 資料庫 → 查詢 → 圖表／地圖的完整流程。
- 維護者：可重現問題、確認資料更新是否成功，並在 API 異常時保留有效資料。

第一版成果是一個能用真實或明確標示的離線資料運作的天氣預報應用。真實資料發布驗收必須完成 API 契約確認；離線展示通過不代表真實串接完成。

## 2. 功能需求與驗收

| ID | 需求 | 驗收方式 |
| --- | --- | --- |
| FR-01 | 擷取候選資料集 `F-D0047-091` | 成功回應解析為資料契約；401／403、429、逾時及非 JSON 均有明確錯誤分類 |
| FR-02 | 保存縣市、預報起訖與最高最低溫 | 使用固定 fixture 核對每筆對應；依縣市與起訖時間配對，不依陣列順序 zip |
| FR-03 | 重複匯入結果一致 | 同一 payload 匯入兩次後有效筆數、值與目前快照不變；失敗批次不能取代成功批次 |
| FR-04 | 縣市與日期選擇 | 選單來自有效資料；切換縣市時重設不再有效的日期；無資料不得沿用前一縣市數字 |
| FR-05 | 顯示最高／最低溫與趨勢 | 摘要與日彙整相符；折線圖依日期遞增，缺值顯示缺口、不補 0 |
| FR-06 | 顯示時段表格 | 表格可核對縣市、起訖、MinT、MaxT、單位與資料批次；與摘要使用同一快照 |
| FR-07 | 地圖日期與代表點 | 地圖顯示所選日期的各縣市資料；點擊代表點同步縣市選擇，日期保持有效；缺少座標的縣市列警示並保留表格 |
| FR-08 | 更新狀態 | 顯示最後成功擷取時間、來源發布時間（若有）、有效期間及更新中／失敗／過期狀態 |
| FR-09 | 無 Key 的示範模式 | 明確啟用 Demo 才載入固定範例；所有頁面標示示範與範例日期；真實更新失敗不自動改成 Demo |
| FR-10 | 載入與空資料狀態 | 初次沒有資料、部分縣市無資料、API 失敗、底圖不可用分別有提示；底圖失敗仍可查表格 |

## 3. 非功能需求

| ID | 品質要求 | 驗收目標 |
| --- | --- | --- |
| NFR-01 | 可重現 | 鎖定依賴；乾淨環境依 README 可安裝與執行 fixture 測試；CI 不需 Key |
| NFR-02 | 資料一致 | 一次畫面渲染固定一個成功批次；更新使用交易；中途失敗不留下可讀的半批資料 |
| NFR-03 | 操作效能 | 約 22 縣市、最多七日 fixture，暖快取篩選至圖表更新目標 2 秒內；記錄硬體、瀏覽器與實測值；不含外部底圖下載 |
| NFR-04 | 密鑰保護 | API Key 僅由伺服器讀取；Git、前端、URL 顯示及錯誤日誌不含 Key；公開錯誤訊息不輸出完整請求 URL |
| NFR-05 | 時間一致 | 內部時間為 UTC，介面為 Asia/Taipei；跨日、跨月、跨年都有案例 |
| NFR-06 | 可操作性 | 在 390px 與 1440px 寬度驗收；篩選具標籤、可用鍵盤操作；顏色搭配數字、文字與圖例；寬表格可局部捲動 |
| NFR-07 | 可觀測性 | 記錄批次 ID、資料集、耗時、筆數、更新結果與安全錯誤代碼；可看出最新成功更新時間 |

## 5. 主要測試情境

1. 正常資料：兩個縣市、不同預報時段，逐筆核對 parser、資料庫與畫面結果。
2. 時間：台北時間午夜、跨年、時段交界與缺少部分日期；半開區間的結束邊界不計入下一日。
3. 缺值：只有 MinT 或 MaxT、無效字串、MinT 大於 MaxT；不可默默補 0 或交換數字。
4. 冪等與修訂：相同 payload 匯入兩次；相同預報時段的新 payload 溫度變更能成為新快照。
5. 故障：授權錯誤、限流、逾時、非 JSON、未知 schema、SQL 寫入中斷；原有效批次仍可查。
6. UI：縣市切換、日期失效、點擊地圖、空資料與缺值；地圖、摘要及表格均使用同一批次。
7. 重建：空資料庫 migration、示範資料啟動、重啟與無網路時的提示。

離線 fixture 測試是 CI 必要檢查；真實 API smoke test 為有密鑰環境的獨立驗證，不能讓 PR 測試依賴外部網路穩定性。

## 6. 風險與處理

| 風險／待確認 | 處理方式 | 解決階段 |
| --- | --- | --- |
| CWA schema 與圖片不同 | 以實際 payload 寫版本化映射與 fixture；變更時明確失敗 | M1 |
| API Key 尚未提供 | 先完成合成 fixture；真實串接保持待驗收，Key 由本機設定提供 | M1–M2 |
| API 頻率與配額未核實 | 快取、有限重試、更新冷卻時間可設定；確認規範後調整 | M2 |
| 縣市名稱／座標不匹配 | 儲存穩定代碼與版本化名稱對照；漏配不得靜默消失 | M1／M4 |
| Streamlit rerun 重複擷取 | 擷取與純查詢分離；快取、更新鎖與按鈕冷卻 | M2–M4 |
| 暫存磁碟遺失 | 示範可重建；需要歷史保存時採持久儲存 | M5 |
| 參考網站功能過多 | P0 驗收完成再逐項開放 P1／P2 | 全程 |

## 7. 完成定義與變更管理

每項功能完成須同時具備需求對應、實作、適當測試、錯誤處理及文件更新。提交訊息簡述行為改變，PR 列出需求 ID、驗證證據與已知限制。CI 建立後，通過檢查才合併。

新增需求先更新 P0／P1／P2 範圍與驗收，再修改架構。發布版本必須標明「示範」或「真實資料」；未完成的工作維持未勾選，不以規畫文件取代程式交付。
